# Imágenes: nombres, etiquetas y de dónde salen

## Referencia completa
`[REGISTRY/]NOMBRE:ETIQUETA`, por ejemplo `auth-backend:1.2.0`
- `NOMBRE`: `S0_IMAGE` / `S1_IMAGE` en `.env.instance` (por defecto auth-backend y gueo-back-end)
- `ETIQUETA`: `S0_TAG` / `S1_TAG`
- `REGISTRY`: vacío = imágenes locales

## Imágenes locales (REGISTRY vacío)
- `deploy` nunca descarga nada de internet
- si la imagen no está cargada, se detiene con error: así Docker no baja de Docker Hub una imagen homónima que no es la nuestra

## Con registry
`REGISTRY=registry.ejemplo.com/itc` hace que `deploy` baje `registry.ejemplo.com/itc/auth-backend:1.2.0`.

## Etiquetas
- usa una etiqueta por versión o por commit; `latest` genera un aviso
- las etiquetas locales son mutables: reconstruir con la misma etiqueta cambia la imagen sin avisar
! `status` y `deploy` lo detectan ("apunta a otra imagen"), pero lo correcto es no reutilizar etiquetas.

## Nombre propio
Si construiste la imagen con otro nombre:
$ docker build -t s0:1.2.0 .
y en `.env.instance` pones `S0_IMAGE=s0`.
- válido: minúsculas, números, `.` `_` `-`; `/` para rutas
- sin `:`; la etiqueta va aparte, en `S0_TAG`

## Arquitectura
Una imagen construida en una PC amd64 no corre en un servidor arm64 (ni al revés).
`./deltactl load` e `./deltactl images` muestran la arquitectura de cada imagen.

## Ver y limpiar
$ ./deltactl images
> Solo lista. Para borrar una concreta: `docker image rm nombre:etiqueta`.
! Evita `docker image prune -a`: borraría también las versiones previas que necesita el rollback.

## Variables del shell
`deltactl` ignora `S0_TAG`, `REGISTRY` y demás variables exportadas en tu shell: solo cuenta `.env.instance`.

## Relacionado
- `./deltactl help actualizar`, `./deltactl help load`
